## 1. 30초 요약

**RAG (Retrieval-Augmented Generation, 검색 증강 생성)** 는 한 줄로 이렇게 정리됩니다:

> **LLM한테 답하기 전에 "우리 문서 좀 찾아보고 답해" 하고 시키는 것**

- LLM 혼자 답하면 → 학습 데이터 기준으로 답함 → 최신 정보나 사내 문서는 모름 → **환각(hallucination) 잘 일으킴**
- RAG 붙이면 → 질문마다 관련 문서를 먼저 찾아서 → LLM 프롬프트에 붙여줌 → **문서 기반 정확한 답**

**시험에 비유하면:**

| | LLM 혼자 | RAG 붙은 LLM |
|---|---|---|
| 시험 방식 | 클로즈드북 | 오픈북 |
| 정답 근거 | 머릿속 (학습 시점) | 지금 찾은 자료 |
| 모르면 | 그럴싸하게 지어냄 | "자료에 없다"고 말함 |
| 답 옆에 | 근거 없음 | "[1]" 같은 인용 있음 |

## 2. 왜 RAG를 붙였나 (실제 예시)

같은 질문을 **RAG 켜고** 한 번, **RAG 끄고** 한 번 던진 실제 결과입니다.

**질문:** "탄군소프트는 어떤 회사인가요?"

### RAG **끔** (`rag=false`) — 순수 LLM

```
탄군소프트는 한국의 소프트웨어 개발 회사로, 
주로 게임 개발에 특화되어 있습니다. 
그러나 제가 가지고 있는 정보는 한정적이고 최신이 아니므로...
```

**결과: 환각.** 게임 회사 아님. LLM이 이름만 보고 짐작해서 지어낸 답.

### RAG **켬** (`rag=true`) — 회사 소개 문서를 넣어둔 상태

```
탄군소프트(TangunSoft)는 서울에 본사를 둔 한국의 소프트웨어 
개발 회사로, 클라우드 인프라, GitHub Enterprise Server(GHES) 
컨설팅, 사내 LLM 시스템 구축 등 주요 사업 영역을 운영하고 
있습니다 [1]. 
임베딩 모델로 multilingual-e5-base를, 벡터 저장소로는 
Chroma를 사용하고 있습니다 [1].

citations:
  [1] tangun-intro.md (유사도 0.90)
```

**결과: 정확 + 인용 표시**. `[1]`이 어느 문서 어느 부분에서 왔는지 응답에 함께 옵니다.

**이게 RAG를 붙이는 이유의 전부입니다.**

## 3. 전체 구조 한 장

```
┌────────────────────────────────────────────────────────────────────┐
│                       사용자 (curl / OpenAI SDK / 웹앱)              │
└─────────────────────────────────┬──────────────────────────────────┘
                                  │  HTTPS (443)
                                  ▼
┌────────────────────────────────────────────────────────────────────┐
│                Apache  (llm.tangunsoft.com)                         │
│                대문 지기: TLS 처리 + 경로 분기                        │
│                                                                    │
│     /rag/*  ─────→  RAG 서비스 (새로 붙인 부분)                       │
│     /*      ─────→  LiteLLM (기존 그대로)                            │
└──────┬────────────────────────────────────────────┬────────────────┘
       │  /rag/*                                    │  /v1/*
       ▼                                            ▼
┌──────────────────────────────────┐    ┌──────────────────────────┐
│   RAG 서비스   (:8100)            │    │   LiteLLM   (:4000)      │
│   FastAPI (Python 3.11)          │    │   OpenAI 호환 프록시       │
│                                  │    │                          │
│   1. 문서 인제스트 / 삭제         │    │   여러 모델을 하나의       │
│   2. 질문 임베딩                  │    │   OpenAI API로 노출        │
│   3. 벡터 검색 (Chroma)           │────┤                          │
│   4. LLM 호출 (LiteLLM 경유)     │    │                          │
│   5. 답변 + 인용 반환             │    │                          │
└──┬───────────────┬───────────────┘    └────────────┬─────────────┘
   │               │                                 │
   │               │                                 ▼
   │               │              ┌──────────────────────────────┐
   │               │              │   vLLM   (:8000)             │
   │               │              │   실제 언어 모델 실행 엔진      │
   │               │              │                              │
   │               │              │   Qwen2.5-7B-Instruct        │
   │               │              │   GPU: NVIDIA L4 24GB        │
   │               │              │   (21GB 점유 중)              │
   │               │              └──────────────────────────────┘
   │               │
   │               ▼
   │    ┌────────────────────────────┐
   │    │  Chroma  (파일 DB)          │
   │    │  /upload/rag/data/chroma/  │
   │    │                            │
   │    │  청크 텍스트                │
   │    │  + 768차원 벡터              │
   │    │  + 메타데이터               │
   │    └────────────────────────────┘
   │
   ▼
┌───────────────────────────────────┐
│  임베딩 모델   (RAG 서비스 메모리 내)│
│  intfloat/multilingual-e5-base   │
│  CPU에서 실행 (GPU 여유 없음)      │
│                                   │
│  텍스트 → 768개 숫자로 변환         │
└───────────────────────────────────┘
```

**핵심 3가지:**
1. **Apache가 문 앞에서 `/rag/*`만 새 RAG 서비스로 보냄.** 다른 경로는 기존 LiteLLM 그대로.
2. **RAG 서비스는 스스로 답을 만들지 않음.** 검색만 하고, 답은 vLLM(Qwen)한테 시킴.
3. **임베딩만 CPU, 실제 답변 생성은 GPU.** 두 개는 완전히 별개.

## 4. 각 부품이 뭐 하는 애인지

| 부품 | 프로세스 | 역할 | 왜 이걸 골랐나 |
|---|---|---|---|
| **Apache** | `httpd` | HTTPS 종단, 경로에 따라 백엔드 분기 | 이미 돌고 있었고 안 건드리는 게 안전 |
| **RAG 서비스** | `uvicorn` (FastAPI) :8100 | 문서 저장 · 검색 · 프롬프트 조립 · 답변 반환 | Python 생태계 최강, 비동기, OpenAI 호환 |
| **임베딩 모델** | RAG 서비스 안에서 로드 | 텍스트를 벡터로 변환 (검색용 지문) | 한국어 잘함 (multilingual-e5) |
| **Chroma** | RAG 서비스 안에 파일로 | 벡터 저장·검색 (벡터 DB) | 별도 서버 필요 없음, 파일 하나면 백업 끝 |
| **LiteLLM** | Python :4000 | OpenAI 스펙으로 여러 모델을 라우팅 | 이미 돌고 있음, 재사용 |
| **vLLM** | Python :8000 | Qwen 모델을 GPU에서 빠르게 실행 | 초고속 LLM 서버, 이미 돌고 있음 |
| **PostgreSQL** | :5432 | LiteLLM이 로그·사용량 저장하는 곳 | 이번 RAG는 **안 씀** (LiteLLM 전용) |

**"기존에 있던 것" vs "새로 붙인 것"**

```
기존 (건드리지 않음):     Apache · LiteLLM · vLLM · Qwen · PostgreSQL

새로 붙인 것:           RAG 서비스 · 임베딩 모델 · Chroma · Apache의 /rag/ 라우팅 3줄
```

기존 서비스를 하나도 안 건드린 게 **의도된 설계**입니다. 사고 나면 롤백만 하면 원상 복구.

## 5. 문서 하나를 넣으면 무슨 일이 일어나는가

예시: 사용자가 `handbook.pdf` (10MB) 를 업로드한다.

```
[사용자] curl -F "file=@handbook.pdf" ... /rag/ingest/file
   │
   │
   ▼
┌────────────────────────────────────────────────────┐
│  Step 1.  PDF에서 텍스트 추출  (pypdf 라이브러리)     │
│                                                    │
│    handbook.pdf  ──→  "1장 소개\n\n우리 회사는..."   │
│                       (긴 텍스트, 예: 30,000자)      │
└────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────┐
│  Step 2.  청킹  (텍스트를 조각내기)                    │
│                                                    │
│    긴 텍스트  ──→  [청크1: 800자] [청크2: 800자] ...  │
│                    청크끼리 120자 정도 겹침 (문맥 보존)│
│                    → 총 40개 청크 나옴               │
└────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────┐
│  Step 3.  각 청크를 벡터로 변환  (임베딩)             │
│                                                    │
│    "우리 회사는 서울에..."                            │
│         │                                          │
│         ▼                                          │
│    임베딩 모델(multilingual-e5-base)                │
│         │                                          │
│         ▼                                          │
│    [0.021, -0.043, 0.128, ..., 0.017]              │
│    ← 768개 숫자 (수학적으로 "이 문장의 의미 지문")     │
│                                                    │
│    ※ CPU에서 실행. 40개 청크 → 약 2~3초              │
└────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────┐
│  Step 4.  Chroma에 저장                              │
│                                                    │
│    각 청크마다 다음 4개를 함께 저장:                    │
│      · 원본 텍스트           (나중에 LLM한테 보여줄 것)│
│      · 768차원 벡터          (검색 시 비교용)          │
│      · doc_id, chunk_index  (어느 문서 몇 번째 조각) │
│      · source, added_at 등  (메타데이터)              │
│                                                    │
│    저장 위치: /upload/rag/data/chroma/  (파일)        │
└────────────────────────────────────────────────────┘
   │
   ▼
[사용자] 응답: { "doc_id": "abc123", "chunks": 40, "bytes": 30000 }
```

**중요 포인트:**
- **원본 텍스트도 함께 저장**됩니다. 그래야 나중에 검색 결과로 LLM에게 보여줄 수 있음.
- **벡터는 검색용 지문**일 뿐이지 답변 소스가 아님. 답변은 원본 텍스트에서 나옴.
- **청킹**을 하는 이유: LLM은 한 번에 볼 수 있는 텍스트 길이가 제한적(예: 8,192 토큰). 문서 전체가 아닌 관련된 조각만 골라서 넣어야 정확도가 높음.

## 7. 왜 CPU로 임베딩하나

이 서버의 GPU (NVIDIA L4, 24GB) 현황:

```
├────────────── 24 GB ──────────────┤
│████████████████████████    │      │
├──────── vLLM(Qwen) 21GB ────┤     │
                             1.7GB만 남음
```

vLLM이 Qwen2.5-7B를 굴리느라 GPU의 대부분(21GB)을 잡고 있습니다. 남은 1.7GB에 임베딩 모델(1.1GB)까지 억지로 올리면:

- 조금만 배치 커져도 **GPU OOM (Out of Memory)** → vLLM이 죽어버림 → **전체 서비스 다운**

그래서 임베딩은 **완전히 격리해서 CPU에서** 실행합니다.

```
[GPU L4]   ← vLLM만 사용   → Qwen 답변 생성 담당
[CPU]      ← RAG 서비스가 사용 → 임베딩 담당
```

**성능 영향:**
- CPU 4코어에서 임베딩: 초당 3~5 청크
- 문서 1개(청크 40개 정도) 인제스트: **약 2~3초**
- 검색(질문 하나 임베딩): **50~100ms**
- 실사용에 충분한 속도. 대량 배치 시에도 background로 넣으면 됩니다.

## 8. 용어 사전 — 이 문서에서 계속 나오는 말들

### 임베딩 (Embedding)
> **텍스트를 숫자 벡터로 바꾸는 것.**

- 이 시스템에서는 `multilingual-e5-base`가 텍스트를 **768개 소수** 로 바꿉니다.
- 같은 의미의 문장은 비슷한 숫자 벡터로 나옵니다.
- 예: "한글 안녕" ≈ "Hello in Korean" (두 벡터가 서로 가깝게 나옴)

### 벡터 (Vector)
> **방향과 크기가 있는 숫자 목록.** 여기선 그냥 "숫자 768개짜리 리스트"라고 생각해도 됨.

### 코사인 유사도 (Cosine similarity)
> **두 벡터가 얼마나 같은 방향을 가리키는지** 를 -1 ~ 1 사이 숫자로 표현.

- 1.0 = 완전 같음
- 0.9 = 매우 비슷 (거의 같은 뜻)
- 0.7 = 비슷 (연관 있음)
- 0.5 = 약간 관련
- 0.0 = 무관

`multilingual-e5-base`는 최소값이 0.7 근처로 좀 높은 편입니다 (특성).

### 청크 (Chunk)
> **긴 문서를 잘라놓은 조각.**

- 이 시스템 기본값: 800자짜리 조각, 조각끼리 120자 겹침
- 왜 자르나: LLM이 한 번에 볼 수 있는 텍스트 길이가 제한적. 관련된 조각만 골라야 함
- 왜 겹치나: 조각 경계에서 문맥이 잘리지 않게

### Top-K
> **검색해서 상위 몇 개 가져올지.**

- 이 시스템 기본 K = 5
- K가 크면 → 더 많은 자료로 답 → 정확도 ↑ but 프롬프트 길어짐
- K가 작으면 → 프롬프트 짧음 but 관련 자료 놓칠 수 있음

### 인용 (Citation)
> **답변이 어느 문서 어느 청크에서 왔는지 표시.**

- 답변 안에 `[1]`, `[2]` 마커
- 응답 JSON의 `citations` 배열에 원본 청크 정보

### 환각 (Hallucination)
> **LLM이 그럴싸하게 지어내는 것.**

- "탄군소프트는 게임 회사" 같은 사례
- RAG의 존재 이유

### Chroma
> **오픈소스 벡터 데이터베이스.**

- 이 시스템에선 **파일 기반**으로 씀 (`/upload/rag/data/chroma/`)
- 별도 서버 프로세스 없음. 백업은 tar만 뜨면 됨

### LiteLLM
> **여러 LLM 백엔드를 하나의 OpenAI 스펙 API로 노출해주는 프록시.**

- 이미 서버에서 돌고 있음
- 이번 RAG는 얘를 통해서 vLLM한테 요청

### vLLM
> **LLM을 GPU에서 초고속으로 서빙하는 엔진.**

- 이 서버는 Qwen2.5-7B를 vLLM으로 서빙 중
- 우리 RAG는 얘를 직접 호출하지 않고 LiteLLM 뒤로 감

## 10. 자주 나오는 질문

### Q1. 문서 하나 지우면 진짜 지워지나?

네. `DELETE /rag/docs/{doc_id}` 로 지우면:
1. Chroma에서 해당 doc_id의 모든 청크 벡터 삭제
2. 사이드카 JSON (`docs.json`)에서 문서 등록 정보 삭제

디스크에서 진짜 사라집니다 (soft delete 아님).

### Q2. 몇 개까지 넣을 수 있나?

디스크 여유가 963GB니까 이론상 수백만 청크 가능.
현실적으론:
- **10만 청크까지**: 검색 여전히 100ms 안팎 (HNSW 인덱스)
- **100만 청크**: 검색 500ms 정도. 임베딩 모델을 더 작은 걸로 바꾸는 게 유리
- **1000만 청크 이상**: 이 아키텍처론 무리. 별도 벡터 DB 서버(Qdrant, Milvus) 검토

### Q3. 같은 문서를 다시 넣으면?

같은 `doc_id`로 다시 `/rag/ingest/text` 하면 **이전 버전이 자동 삭제**되고 새 버전으로 교체됩니다. 문서 갱신 시 편리.

`doc_id`를 안 주면 매번 랜덤 ID로 새로 들어감(중복 저장).

### Q4. 답변이 이상하다. 어디서부터 봐야 하나?

**5단계 디버깅:**

1. **`/rag/search`로 검색만 해보기** — 관련 청크가 잘 잡히는지
   - top-1 유사도 0.85 이상 나오면 검색은 OK, 아래 단계로
   - top-1이 낮으면 → 청킹/임베딩 모델 문제
2. **인용된 원본 텍스트 읽어보기** — 응답의 `citations[].snippet` 확인
   - 답과 다른 얘길 하고 있으면 → 청킹이 문맥 자름
3. **RAG 없이 같은 질문** (`rag=false`) 던져보기
   - 원래 LLM도 못하는 질문이면 → 모델 한계
4. **`/rag/debug/similarity`로 페어 비교**
   - 질문과 이상적 정답 텍스트 유사도 0.75 이상 나와야 정상
5. **로그 확인**: `sudo journalctl -u rag.service -n 100`

### Q5. PDF에 이미지만 있는데 되나?

**안 됨.** 이 시스템은 pypdf로 텍스트만 뽑습니다. 스캔본 PDF 처리하려면 OCR 필요 (Tesseract, `pdf2image` + `pytesseract`). 현재 미구현.

### Q6. 스트리밍 응답 되나?

네. `/rag/v1/chat/completions`에 `stream: true` 붙이면 SSE(Server-Sent Events)로 흘려보냅니다. RAG는 사전에 검색 완료 후 스트림 시작.

```python
from openai import OpenAI
client = OpenAI(base_url="https://llm.tangunsoft.com/rag/v1", api_key="sk-...")
for chunk in client.chat.completions.create(
    model="qwen2.5-7b",
    messages=[{"role":"user","content":"..."}],
    stream=True,
    extra_body={"rag": True},
):
    print(chunk.choices[0].delta.content, end="", flush=True)
```

### Q7. 검색 언어와 문서 언어가 다르면?

**됨.** `multilingual-e5-base`는 다국어 임베딩이라서 "How to cook kimchi stew?" (영어 질문) → 한국어 김치찌개 레시피 문서 매칭이 가능합니다.

다만 이 사이즈 모델은 KO→EN 방향이 살짝 약함. 정확도가 중요하면 `BAAI/bge-m3`로 교체 검토.

### Q8. RAG 서비스가 죽으면 다른 LLM API에 영향이?

**없음.** `/rag/*` 만 새 서비스로 가고, 기존 `/v1/*` (LiteLLM 직통)은 그대로. 즉:

- RAG 서비스가 죽으면 → `/rag/*` 만 502
- vLLM/LiteLLM/Apache 는 계속 정상

의도된 격리 설계.

### Q9. 문서 안 넣고 그냥 질문하면?

문서가 0개인 상태로 `/rag/query`를 부르면:
- 검색 결과 없음
- 프롬프트에 `"(no relevant context found)"` 삽입
- LLM이 "자료 없다"고 답하도록 유도

즉 자연스럽게 실패합니다. 크래시 안 남.

### Q10. 인증은 어떻게?

현재 **인증 꺼져 있음**. 켜려면:
1. `/upload/rag/rag.env`에 `API_KEY=원하는_비밀키` 추가
2. `sudo systemctl restart rag.service`
3. 이후 모든 요청에 `X-API-Key: 원하는_비밀키` 헤더 필요 (`/rag/health` 제외)
